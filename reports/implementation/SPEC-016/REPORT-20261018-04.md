## Outcome and changes

Implemented the approved HTTP-only security foundation in the existing shared package, using Node built-ins and the already locked Ajv/contracts dependencies. No dependency, infrastructure, Actor, crawler, source adapter or SQL implementation was added. The first discovery crawler remains SPEC-003.

- `runtime-security.ts` validates explicit development/test configuration, source/context/version/scope, rate group, finite budgets, evidence policy and role/secret references. Environment designation must match trusted `DAAS_ENV`. It snapshots and freezes configuration and secret values separately; hashes/public state omit secret values. Validated sessions are registered in a private WeakMap, so serialized or forged objects cannot authorize HTTP. Browser/proxy/production startup rejects.
- Actor roles can access only explicitly declared Apify environment references. They cannot load SQL values or alias the Apify reference to a SQL environment name. Integration configuration declares exactly control read/write and Bronze insert intent, with its own Apify/SQL references; admin and Bronze update/delete intent reject. This does not execute or verify SQL grants.
- `network-address.ts` checks complete bounded DNS sets, family/syntax and public destination policy before connection. Any restricted/malformed answer denies the set. Address comparisons handle equivalent socket-peer representations without treating comparison as authorization.
- `secure-http.ts` implements direct GET with fresh isolated agents, no ambient/global proxy or connection reuse, a pinned validated literal IP and the original Host/TLS SNI/certificate hostname. Every redirect repeats normalization, scope, path and DNS authorization. Unknown compression/protocol upgrades reject. Fixed header and separate streaming wire/decoded caps prevent unbounded response accumulation.
- Wall-clock cancellation covers hung DNS, TCP/TLS handshake, response headers and body. Clients created from the same session share request count, concurrency, spacing and run start. Local loopback success requires trusted test startup plus a separately supplied exact origin/port/address capability; untrusted JSON cannot select it.
- `evidence-security.ts` validates descriptor policy and ownership using SPEC-002 reference validation, exact provider/location/retention class, policy/context revisions, safe key prefixes and byte caps. Returned policies/descriptors are frozen snapshots. No storage is selected, contacted or provisioned.
- SPEC-004's existing normalizer schema is reused internally without changing normalization behavior. The dependency graph now explicitly contains 004 → 016, with 18 nodes/38 edges. Public exports, development guidance, safe environment examples and authority/index records reflect this scope.

## Decisions, limits and follow-through

The user approved only controlled HTTP fixtures, environment-secret loading and explicit caller policies/test ceilings. Limits remain explicit: 5 physical requests, 10 candidates, depth 1, concurrency 1, at least 1,000 ms spacing, 3 redirects, 1 MiB wire and decoded body, 20 s request/120 s run, DNS ≤ request ≤ run, at most one declared retry and zero rotations/restarts. Redirect/retry allowances must fit the request ceiling. The client adds no automatic retries. Candidate/depth/retry fields are exposed for the crawler; cross-session/run site admission belongs to 009/014. A caller creating independent runtime sessions does not obtain shared rate-group enforcement from this local client.

IPv4 deliberately denies all special-purpose allocations, including some globally reachable services, plus multicast/reserved and Azure `168.63.129.16`. IPv6 permits only `2000::/3`, excluding special/transition/documentation prefixes including `2001::/23`, `2001:db8::/32`, `2002::/16`, `2620:4f:8000::/48` and `3fff::/20`. Mapped/translated/tunnel forms do not gain authorization. This conservative policy can reject legitimate special services; changing it needs review and vectors. [IANA IPv4](https://www.iana.org/assignments/iana-ipv4-special-registry/), [IANA IPv6](https://www.iana.org/assignments/iana-ipv6-special-registry/), [Azure platform address](https://learn.microsoft.com/en-us/azure/virtual-network/what-is-ip-address-168-63-129-16).

TLS fixtures use existing OpenSSL to generate temporary fixture-only keys/certificates. No private key is committed. Windows setup currently expects the documented Git OpenSSL location; Linux uses `openssl` on PATH. Missing tooling fails setup. Tests exercise successful IPv4 loopback sockets and IPv6 classification/peer comparison, not an actual IPv6 server or every OS/network route. Address rules do not replace an approved production egress boundary. The Node request/agent mechanisms follow [Node 24 HTTP documentation](https://nodejs.org/docs/latest-v24.x/api/http.html); full-route validation follows [OWASP SSRF guidance](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html).
