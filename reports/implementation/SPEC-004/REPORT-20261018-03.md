Resolves references only against explicit valid bases, checks the final origin and segment-aware path scope, and returns original plus canonical URL with source/context/version and identity metadata.

Exact identity-key comparison distinguishes equality, difference, collision and inconsistent hash metadata. No production weak-hash hook exists.
- Private `@daas/shared` source entry point and locked dependencies on local `@daas/contracts` `0.0.0` and already verified Ajv `8.20.0`. No new third-party library/version was selected. Type-only schema inference uses existing workspace development tooling.

## Decisions and limits

[ADR-0003](../../../docs/architecture/decisions/ADR-0003-url-identity.md) records the user-approved shared module with synthetic fixtures. V0.2 explicitly replaces the draft requirement to have real source rules before implementation with the narrower trusted-policy/preservation scope. Parameter removal, query sorting, alternate fragment/slash transformations and canonical/redirect aliases are intentionally unsupported pending approved real-source vectors/version/migration decisions. This is no blanket approval of D-02/D-05 or SQL D-03.

URLs/bases/canonical URLs are bounded at 2,048 code points; origins and prefixes at 10 each; keys at 4,096 UTF-8 bytes; shared JSON bounds apply. Raw Unicode can exceed the serialized URL limit after percent expansion and is rejected rather than truncated. Bases are syntactically validated even for absolute targets; final target scope is enforced separately. Original references may be relative, so future producers must satisfy their absolute discovered-URL contract explicitly.

Only syntax and literal serialized path scope are checked. Encoded separators can be decoded differently by servers; DNS/connection/redirect/browser egress enforcement remains SPEC-016. No caller-supplied policy here proves permission to fetch. Policy meaning and context dimensions must be registered immutably by later owners. Hashes are lookup/integrity data, not authentication. Comparison accepts exact metadata pairs and validates key shape, without recomputing the supplied digest; intake must recompute/store trusted hashes.
